## Why this matters

Section 18 (SQL Monitor) ends with an "Execution scatter": every captured
SQL execution as a dot, x = start time, y = elapsed (log scale), capped at
3,000 points. In the demo report it is a solid band of overlapping circles:

- **Mark size**: size = `5 + 2 × requested DOP`, capped at 18 px. In the
  demo 509 of the 3,000 points are DOP 8, so they are 18 px circles at 85 %
  opacity; they cover everything under them.
- **Nothing marks the Current window** except the shaded band behind the dots.
- **The cap hides most compared windows.** The cap keeps the 3,000 *most
  recent* executions. The demo span is 18 Jun–10 Sep, 13 weekly windows, and
  13,205 captured executions; the kept 3,000 cover only 22 Aug–10 Sep.
  Counting the points per window in the demo's payload: **10 of the 13
  compared windows contain zero points** (w-12 … w-3 = 0; w-2 = 7, w-1 = 7,
  Current = 9). A chart meant to compare windows shows only the last three.

After this plan: smaller marks scaled by `log2(DOP)`, faded except the
Current window's points (solid, outlined), errors and plan changes always
solid; the x-axis always spans the whole compared span; and (step 5, owner
decision) the cap keeps executions that fall in a compared window first,
then the most recent — so every window shows its executions.

### Step 5 (owner decision, separate commit): keep compared-window executions under the cap

The cap stays 3,000 and the payload shape stays the same; only *which*
executions are kept changes: those that start inside a compared window come
first (most recent first among them), then the rest by recency. Window
membership is computed arithmetically from the nominal window grid — no
join, no second read of `DBA_HIST_REPORTS`:

In the points query, add a column to the innermost `be0` select list (after
`NVL(x.elapsed_us, 0) AS elapsed_us`):

```sql
                               -- 1 when the execution starts inside a compared
                               -- window (nominal grid: windows_cte.sql's rule)
                               , CASE WHEN MOD(TO_DATE('~target_end_resolved', 'YYYY-MM-DD HH24:MI:SS')
                                               - TO_DATE(r.key3 DEFAULT NULL ON CONVERSION ERROR, 'MM:DD:YYYY HH24:MI:SS'),
                                               (~step_hours/24)) < (~win_hours/24)
                                      THEN 1 ELSE 0 END AS in_win
```

Carry it up: the `plan_cnt` level selects `be0.*`, so it passes through by
itself; the `mode_plan` level lists its columns explicitly
(`SELECT b.sql_id, b.exec_start, b.elapsed_us, b.status, b.plan_hash, b.px_req, MAX(…) … AS mode_plan`)
— add `b.in_win,` to that list. The level above (`be`) only needs it inside
the analytic. Change the cap's ordering:

```sql
                   ROW_NUMBER() OVER (ORDER BY be.in_win DESC, be.exec_start DESC) AS rn_recent,
```

No comment inside this query may end with `;` (it is one SQL statement in a
`FOR … IN ( … ) LOOP`). Then change the cap note's text to
`"Capped to 3,000 of "+AWR_DATA.sqlmon.totalRaw+" captured executions: those in the compared windows first, then the most recent."`
(keep the line's `if(el0){var note=` prefix), and in the file header
comment (line 41) "capped at 3,000 most-recent points" → "capped at 3,000
points, compared-window executions first".

Twin (`s18_sqlmon.py:581-583`): with `end = w.target_end`,

define `in_win(m) = 1 if (end - m.exec_start) % step < win else 0`
(Python's `timedelta % timedelta` is supported) and sort with
