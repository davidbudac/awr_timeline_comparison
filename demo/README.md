# Demo report generator

`docs/examples/demo_busy_db.html` is a **synthetic showcase report**: what
`awr_trend.sql` produces against a very busy production database over a
three-month span, with releases and an upgrade marked on the timelines.
It is generated by the pure-Python code in this folder — no Oracle
involved — so the project website can show the full report (the Summary,
Timeline and All sections views, every toggle, hourly ASH over 12 weeks)
without a busy 19c database to run it on.

This folder is **tooling for the docs site only**. It is not part of the
toolkit: the real report is still pure SQL\*Plus, still read-only, and
nothing under `sql/`, `awr_trend.sql` or the wrappers depends on it.

```sh
python3 demo/gen_demo_report.py                      # -> docs/examples/demo_busy_db.html (ECharts inlined, offline)
python3 demo/gen_demo_report.py --cdn out.html       # link ECharts from the public CDN instead
python3 demo/gen_demo_report.py --only=06_top_sql x.html   # one section (debugging a port)
node demo/verify_report.js docs/examples/demo_busy_db.html shots/   # headless smoke test + screenshots
# no node_modules in the repo: point NODE_PATH at any playwright install, e.g.
#   T=$(mktemp -d); (cd $T && npm i playwright@1.55); NODE_PATH=$T/node_modules node demo/verify_report.js ...
```

## How it stays faithful to the real report

* **Chrome is lifted, not copied.** `awrdemo/chrome.py` evaluates the
  literal `DBMS_OUTPUT.PUT_LINE` calls of `sql/_style.sql` and
  `sql/lib/js_*.plsql` (`lib_script(name)`: js_wait_colors, js_microstrip,
  js_markers, js_wingrid, js_timeline — the generated ones included) at
  generation time, so the demo carries the exact CSS / shared-JS bytes of
  the current sources. The section ports lift their `<script>` blocks the
  same way.
* **Number strings are Oracle-faithful.** `awrdemo/helpers.py` twins
  every shared PL/SQL lib: `fmt_num` / `fmt_int`, `metric_policy` /
  `policy_bucket` (it parses `sql/lib/metric_policy.plsql` itself),
  `score_cells`, the band glyph (`band_*`, `delta_span`, `range_txt`,
  `lib_ls`), `anchor_id` / `finding_anchor`, the card vocabulary
  (`card_*`, `metric_*`, `fv*`, `ent`, `card_order`), the window component
  (`wg_*`), the Timeline rows (`tl_*`), `is_essential`, `is_oracle_schema`,
  `DBMS_XMLGEN.CONVERT` and the `TO_CHAR` masks (half-away-from-zero
  rounding, `FM` trimming, `D0` mandatory decimals).
* **One section, one port.** Each `awrdemo/sections/sNN_*.py` is a
  hand-ported twin of `sql/NN_*.sql`: same elements, ids, classes,
  `data-*` hooks, JSON payload shapes, captions. `PORTING.md` is the
  contract. When a section's markup changes, re-port that section.

## The synthetic world (`awrdemo/model.py`)

One deterministic hourly model (seeded RNG, stable output) feeds every
section, so the report is internally coherent: a spike in DB time is
visible in the verdict, the DB time strip, the finding cards, the Timeline,
the ASH charts, the wait tables, Top SQL, segment and file I/O and the
likely-source line at the same instant.

| | |
|---|---|
| Database | `ORCLPRD`, 19c, single instance, 16 CPUs, hourly AWR snapshots |
| Comparison | Thursday 09:00–10:00, weekly cadence, 12 prior weeks (`target_end='2026-09-10 10:00'`, `weeks_back=12`) |
| Baseline | OLTP order-entry (checkout, lookups, inventory) + hourly reporting; ~10–13 AAS at 55–70 % host CPU on weekdays, nightly batch 01:00–03:00, quiet weekends, +9 % growth over the quarter |
| Extras on | `profile_days=7` (Day profile), inline `markers` |

Marked milestones, each with its own signature:

| When | Marker | What the report shows |
|---|---|---|
| 2026-06-30 22:00 | Release 4.0 | hard-parse storm (×15), library-cache mutex / cursor-pin contention, CPU up, ~2.5 days; the −10w window sits inside it |
| 2026-07-03 09:00 | Hotfix 4.0.1 | `cursor_sharing` EXACT→FORCE ends the storm |
| 2026-07-21 01:00 | RU 19.28 patch | instance bounce (startup time changes, `sga_target` raised), cold buffer cache for ~3 h |
| 2026-08-11 22:00 | Release 4.1 | Loyalty feature: two new SQL_IDs, +12 % steady load, one day of `enq: TX - row lock contention`; `pga_aggregate_target` raised |
| 2026-09-08 22:00 | Release 4.2 | `optimizer_adaptive_plans` TRUE → the order-lookup statement flips plan (index → full scan of ORDER_LINES): physical reads ×4, User I/O ×3, DB time ×1.6 — **still ongoing at target_end, so the Current window is the regression** |

Unmarked blips: month-end close batches (Jul 31, Aug 31 evenings) and a
90-minute `log file sync` storage incident on Aug 25 14:00.

## Regenerating

The output is deterministic (two runs, same md5); re-run the generator
after changing the model or a port and commit the resulting HTML.
`verify_report.js` loads it in headless Chromium (or system Chrome) and
fails on any page/console error in any of the three views (Summary /
Timeline / All sections) in light and dark, on an in-page href that does
not resolve to exactly one id, or on a duplicate id. It also exercises the
view switch and its persistence, cross-view jumps, rail dimming, tabs,
sort and expanders; clicks every visible entity link (`a.ent`) and checks
its target is shown; walks the Timeline (lanes, `data-tl` jumps, label
links, chart hover / legend / zoom / reset / double-click, pin / unpin,
keyboard); checks plan cards, the evidence library rows and their toggle,
the rail sub-links, that All sections shows every section in full, and the
micro strips; and writes a screenshot per view x theme. It runs against
any report (dbmint's too) in ~3 minutes; run one instance at a time
(parallel runs hang Chrome).
