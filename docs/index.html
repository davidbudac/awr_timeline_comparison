Install clone the repo; grant SELECT on a handful of DBA_HIST_* views

There is nothing to install in the database: no scratch schema, no packages, not a single write. Clone the repository on any machine with SQL*Plus and run.

  • Oracle Database 19c with the Diagnostic + Tuning Pack licensed (the toolkit reads DBA_HIST_*).
  • A user that can read the AWR views: any DBA account, or a dedicated analyst granted SELECT on the views listed in the README. A read-only standby that exposes AWR works too.

Fleet console many databases, one worst-first page — run_awr_fleet.sh

The mode most teams want: point run_awr_fleet.sh at a list of databases and get one self-contained, worst-first ops console. It runs the same aligned-window z-score comparison against every database in parallel and sorts the rows so the sickest database is the first one on the page.

Each database is one dense, collapsed row: status dot, severity score, crit/warn pills, current AAS, its worst finding, a DB-time sparkline and a 24-hour ASH-by-wait-class ribbon. Click a row and it expands in place into a full detail panel: a tall ASH timeline, headline metric cards, the findings table and the Top SQL table.

fleet.conf — one alias | connect per line
# alias        | connect
prod-emea      | /@PRODEMEA
prod-amer      | /@PRODAMER
reporting      | reporting_ro/@RPT
one command, the whole fleet
./run_awr_fleet.sh fleet.conf

# mark a fleet-wide event on every DB's 24h ASH chart:
MARKERS='2026-04-20 14:00|Applied patch 19.22' ./run_awr_fleet.sh fleet.conf
BehaviourWhat you get
Failure is loudA database that is unreachable, times out, or spools a truncated fragment becomes a red error row sorted to the top. Silence is never mistaken for health.
Drill-downEvery row prints the exact command to open the full single-DB report for that database; FLEET_DETAIL=all generates them in the same run.
MarkersFleet-wide timeline markers are drawn on every database's ASH chart at the same instant, so a release or patch lines up visually across the estate.
Day profileFLEET_PROFILE_DAYS=7 adds an hour-of-day heatmap to every detail panel: each hour of the last 24 h against the same hour on the prior days.
OfflineInline-SVG only, no CDN, credentials masked in every log and report. One folder per run, relocatable as a whole.

Full reference — fleet.conf format, scoring, every environment variable — in the Fleet section of the README.

Single database is it behaving the way it did before? — run_awr_trend.sh

The single-DB report lines up the same hour of the same weekday across the past weeks (this Thursday 09:00–10:00 against the twelve prior Thursdays, say) so the normal weekly rhythm is never mistaken for a problem, and grades every metric against its own history: |z| > 2 moderate, |z| > 3 large.

Inside the report every section is a white panel, every panel a rail link

Rail groupSectionsReads
TriageDB time over the full span, headline cards, hourly ASH timeline by wait class, findings with the biggest movers, aligned windowsSYS_TIME_MODEL, SYSSTAT, ACTIVE_SESS_HISTORY, SNAPSHOT

Client-side toggles ship in every report: dark mode, Triage mode (only the sections that matter first), Essential rows (the curated short lists), Application only (hides Oracle-internal SQL), a row filter, click-to-sort headers and CSV / Markdown export per table.

Common runs

# defaults: current hour vs the same hour on the 4 prior weeks
./run_awr_trend.sh user/pw@svc

# a specific Monday morning vs the 4 prior Mondays
./run_awr_trend.sh user/pw@svc '2026-04-13 09:00'

# last 4 hours, hour by hour
./run_awr_trend.sh user/pw@svc AUTO 1 4 10 0 1 h

# lean triage report
./run_awr_trend.sh user/pw@svc AUTO 1 4 10 0 1 w simple

# annotate the timelines with your own milestones
MARKERS='2026-04-20 14:00|Applied patch 19.22' ./run_awr_trend.sh user/pw@svc

# + Day profile (last 24 h vs the 7 prior days) + plan-line drift for the top 3 regressed statements
./run_awr_trend.sh user/pw@svc AUTO 1 4 10 0 1 w comprehensive Y '' 7 3

# fully offline, self-contained file (ECharts inlined from vendor/)
ECHARTS=vendor/echarts.min.js ./run_awr_trend.sh user/pw@svc
pure SQL*Plus — no shell required (Windows-friendly)
SQL> @sql/defaults.sql
SQL> @awr_trend.sql

-- or customize one-off:
SQL> DEFINE target_end = '2026-04-15 09:00'
SQL> DEFINE win_hours  = 2
SQL> DEFINE weeks_back = 6
SQL> @awr_trend.sql

Unsure about the argument order? ./run_awr_trend.sh --configure walks you through every option with defaults and validation and prints the ready-to-paste command. The web configurator does the same in your browser, and the cheat sheet has the full argument reference plus ready-to-paste recipes: hour-by-hour walkthroughs, batch-window checks, quarter-over-quarter, offline reports, markers.

The report lands in reports/awr_trend_<DB>_<DBID>_<timestamp>_run<run_id>.html. Open it in any browser, attach it to a ticket. RAC and multitenant (PDB / migrated PDB) are handled; when history is too short to score fairly the report says insufficient history instead of guessing.

Templates same engine, different altitude — the template argument

The template argument picks which curated set of metrics and wait events the single-DB report renders:

TemplateForWhat it renders
comprehensiveDBAs defaultThe full curated lists and the complete firehose of wait events ranked by time.
simpleTriageA quick-glance subset you skim in thirty seconds before deciding whether to dig.
devApplication teamsWhat the application itself drives: throughput, query work, parsing, SQL*Net chattiness, app-caused contention. Host/OS and storage internals left out.

Rolling your own is a directory with three files under sql/lib/templates/<name>/ plus one whitelist entry in the driver. See the README.
