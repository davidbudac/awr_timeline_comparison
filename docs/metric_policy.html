The rule, step by step

Every scored value is the Current window compared with the prior windows (the same hour on the previous days or weeks). One bucket per row, computed by policy_bucket():

  1. Enough history? Fewer than 3 prior windows → insufficient history. No usable spread (all priors identical and zero) → flat baseline. No Current value → n/a.
  2. How unusual? z = (Current − prior mean) ÷ max(σ, 2% of |prior mean|). The 2% floor stops a dead-flat baseline from turning a trivial wobble into a huge z. |z| ≤ 2 → typical.
  3. Is it material? The metric's own minimum %-delta must be met (|Current − mean| / |mean|), and its value floor: at least one of Current / prior mean must reach the floor in the metric's unit (for waits: the row's share of the Current window's non-idle wait time must reach the minimum share). Otherwise typical, badged immaterial.
  4. Which direction? Per metric: UP (rise is bad), DOWN (drop is bad), ANY (both), INFO (never a finding). A material move in the good direction → improved; an INFO counter that moved → noted. Neither is highlighted, listed as a mover, or counted in the verdict.
  5. How big? |z| > 3 → large, otherwise moderate. A table-wide shift in the wait tables demotes large to moderate.

Worked example. Hard parses (parse count (hard): rise is bad, min 25%, floor 2/s). Prior windows 0.1, 0.1, 0.2, 0.1 /s; Current 0.6 /s. z is about 8 and the move is +500%, but both values sit below the 2/s floor → typical, immaterial. Prior windows 12, 11, 13, 12 /s; Current 18 /s: z about 7, +50%, above the floor, a rise → large. Prior 12 /s, Current 6 /s: a drop → improved, shown muted, not counted.

Directions and buckets

UP rise is bad
A rise is a finding; a drop is improved (never highlighted).
DOWN drop is bad
A drop is a finding; a rise is improved (never highlighted).
ANY either way
Both directions are findings: a drop can be an outage, a rise a storm. Nothing is called improved.
INFO informational
Never a finding. A material move renders as noted (grey, not counted).
large|z| > 3, material, bad direction. Counted in the verdict, listed in Biggest movers, row tinted. moderate|z| > 2, material, bad direction. Counted, listed, tinted. typicalInside the usual spread, or the move was immaterial (badged). improvedMaterial move in the good direction. Muted badge, no tint, never counted; the verdict says "N improved". notedAn informational counter that moved. Grey, never counted. skipn/a, insufficient history or flat baseline: not scored.

Wait classes and events (DBA_HIST_SYSTEM_EVENT / BG_EVENT_SUMMARY)

Scored on time waited per second. Every wait is UP (less waiting is never a problem). The floor is a share: the row must hold at least that fraction of the Current window's total non-idle wait time, so a wait that tripled but is 0.3% of the total never fires. A per-event line overrides its class; a class not listed uses the default (rise ≥ 15%, share ≥ 2%).

How to change it

  1. Edit the metric's line in sql/lib/metric_policy.plsql. Keep the one-line shape WHEN 'name' THEN RETURN pol('FAMILY', 'Y', 'UP', 20, 50); (or wpol(v_class, 'UP', 15, 0.02) for waits): the demo generator and this page parse those lines.
  2. Floors are in the metric's own unit (see the unit under each name). Set a floor to NULL to remove it. Wait floors are shares between 0 and 1.
  3. To stop a metric from ever being a finding, set its direction to INFO. To make a drop count as a problem too, use ANY.
  4. A new stat or metric added to a template needs a line here, or ./lint.sh (check 12) fails and the stat falls back to the generic default.
  5. Run ./lint.sh, then python3 docs/gen_policy_doc.py and python3 demo/gen_demo_report.py.

The same policy drives the single-DB report (verdict, findings, headline cards, wait tables, day profile, narrative) and the fleet report's findings band, row worst-finding and headline cards.
